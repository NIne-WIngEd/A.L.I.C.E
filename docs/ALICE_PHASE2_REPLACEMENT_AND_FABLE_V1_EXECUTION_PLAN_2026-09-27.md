**Date:** 2026-09-27

**Scope:** all work from the current N0 branch through final Phase 2 replacement and the first full Fable release

## 0. Non-negotiable interpretation

Fable v1 is **not** a reduced, lightweight, small-scale, minimal-daemon, or narrow-gate version of the destination.

The first release carries the **full transferable personal/cognitive architecture** described by:

- the Fable README and FIRST_RELEASE specification;
- *The Second Mind* comic;
- A.L.I.C.E./Friday flagship parity governance;
- Friday Product Vision and Architecture;
- Memory Architecture v4.1;
- Fable Personal Development Architecture;
- Capability Catalog and no-capability-ceiling doctrine.

Only replaceable **feature-model work** may be delegated to external GPT/Claude-class services in v1: broad prose generation, coding, research, simulation, vision/image generation/editing, and similar general feature capabilities. Those services do not own identity, personal memory, user understanding, relationship state, self state, native judgment, memory formation, retrieval policy, Experience learning, mission state, personal model evolution, or continuity.

The governing product rule is:

> **Least vendor knowledge, not least local intelligence.**

And the governing engineering rule is:

> **Deployment topology may adapt to hardware. Cognitive capability may not be removed to simplify deployment.**

A local machine, workstation, NAS, private cluster, or later multi-region deployment may instantiate the same logical plane with different physical placement. That is hardware adaptation, not a different capability class.

## 6. Lane D — full Memory v4.x successor

The old "PostgreSQL for event + claim and simplify the rest" decision is superseded.

The successor is a **full polyglot personal cognitive fabric**. Logical planes exist because they solve different memory problems.

### D1 — Raw Evidence/Object plane

Stores originals and durable payloads:

- text;
- images;
- audio;
- video;
- code;
- documents;
- sensor/scientific artifacts;
- model/data/checkpoint artifacts;
- exact permissions and provenance.

Use encrypted content-addressed storage with an S3-compatible abstraction. Local disk/NAS/private object cluster/cloud bucket are placements of the same plane, not capability classes.

### D2 — Experience/Event Fabric

Selected architecture: **event-stream-native, replayable append-only fabric**.

Current physical default: **NATS JetStream** behind A.L.I.C.E./Fable-owned `EvidenceLog` and event-envelope contracts.

Why:

- persistent replayable streams;
- durable consumers;
- replication;
- local/edge/distributed deployment;
- Apache-2.0 distribution;
- one server family can span desktop, LAN, private cluster and multi-device edge topology.

A.L.I.C.E./Fable code owns:

- event identity;
- expected-stream/version semantics;
- idempotency;
- evidence binding;
- causal/device clocks;
- correction/deletion lineage;
- custody classes;
- projection checkpoints.

**KurrentDB remains a strong event-native reference/challenger**, but its KLv1 non-OSI license makes it a poor dependency to hard-code into the entire Fable product family. This is a product-architecture decision, not a claim that KurrentDB is technically weak.

### D3 — Claim Authority

Selected architecture: **XTDB v2-class native bitemporal authority**.

Current physical default: **XTDB v2**.

Every accepted Claim requires:

- claim identity and versions;
- system/transaction time;
- valid/effective time;
- provenance/evidence;
- confidence/uncertainty;
- conflict;
- source hierarchy;
- supersession/correction;
- deletion/revocation;
- authority generation.

XTDB's automatic valid-time + system-time history is a closer semantic match than hand-building all bitemporal behavior in ordinary PostgreSQL.

Its per-database single-writer indexing model is not treated as a product ceiling: Claim acceptance is deliberately serialized authority work and may be host/authority-sharded when a deployment requires more write throughput. Reads and storage topology can scale independently.

### D4 — Episodic/Autobiographical plane

Maintain learned episodes distinct from raw event history and canonical claims.

Each episode can include:

- start/end and uncertain boundaries;
- participants;
- source events;
- narrative;
- goals/outcomes;
- place/environment;
- affect/appraisal;
- mission/project relation;
- dynamic scene/domain memberships;
- later reinterpretations.

Episodes are derived, versioned and rebuildable.

### D5 — Cognitive Multi-Graph plane

This is not one monolithic "knowledge graph."

Each memory item may participate in orthogonal graph views:

- entity;
- semantic/concept;
- temporal;
- causal;
- evidence/provenance;
- social/relationship;
- mission/project;
- goal/dependency;
- skill/procedure;
- source trust;
- identity/person;
- world model;
- model/dataset lineage;
- outcome/decision.

The views share registered node/evidence identities but do not collapse their edge semantics.

**Local embedded graph engine:** LadybugDB is the current preferred host-local engine because it is MIT-licensed, embedded, ACID, columnar, multi-core, Cypher-capable and provides graph algorithms.

**Scale-out graph engine:** JanusGraph on an appropriate distributed backend is the current private-cluster path when one host's graph materially exceeds a single-machine placement.

This is **not** a reduced-vs-full profile. It is the same graph contract with hardware-adaptive placement.

Neo4j remains a proven A.L.I.C.E. projection/reference and useful research backend. It is not made the sole Fable graph dependency because Community GDS imposes a four-core algorithm limit and clustering/scale features are commercial.

### D6 — Associative graph-compute plane

Graph storage is not enough.

Add engine-independent retrieval computation supporting:

- personalized PageRank;
- spreading activation;
- temporal decay;
- lateral inhibition;
- path/bridge discovery;
- relation-view weighting;
- community/cluster signals;
- query-conditioned multi-graph traversal.

All scores are **retrieval accessibility**, never factual authority.

This layer incorporates useful ideas from HippoRAG 2, SYNAPSE and MAGMA without copying any paper's ontology as a ceiling.

### D7 — Vector/Multimodal retrieval plane

Selected engine family/current default: **Qdrant**.

Use:

- dense vectors;
- sparse vectors;
- named vectors;
- multivectors / late interaction;
- payload filters;
- multiple model generations;
- text/code/image/audio/video/scientific representations;
- host/namespace isolation;
- local/edge or distributed deployment.

The vector plane is part of the full Fable architecture. The Context Planner may choose not to use it for a particular query. "Not used for this query" is different from "missing from Fable."

### D8 — Source-native retrieval plane

Keep exact and live retrieval first-class:

- files;
- database rows;
- FTS;
- metadata;
- git/code search;
- mail/calendar/drive/live systems;
- tool/API queries;
- source section/table/figure navigation.

LongMemEval-V2-style evidence gathering is a reminder that an agent can outperform fixed RAG when it searches the source itself. This plane complements graph/vector memory.

### D9 — Multimodal perceptual identity memory

Do not reduce people, voices, objects, places or visual/audio patterns to captions.

Maintain grounded host-private representations such as:

- face/person embeddings when authorized;
- speaker/voice embeddings;
- object/place representations;
- image/video region keys;
- audio event keys;
- cross-modal links back to exact source evidence.

A small in-model or learned personal memory bank may accelerate recognition, but source/evidence authority stays external and deletion influence remains traceable.

### D10 — personal cognitive-model projections

The full fabric supplies versioned state for:

- source-person identity model;
- user/host model;
- assistant/Fable self;
- relationship model;
- world model;
- social model;
- causal model;
- source-trust model;
- preference/value model;
- mission/goal model;
- skill/procedure model;
- predictions and outcome history.

These are not necessarily one model each and not necessarily one storage technology each.

### D11 — parametric personal memory

Fable may learn personal knowledge into:

- EIPM/identity weights;
- MFM weights;
- host/relationship/self updaters;
- retrieval/ranking models;
- adapters;
- procedural policies;
- perceptual memory banks;
- future native conversation/reasoning models.

Parametric memory is powerful but is never permitted to become the only record of authoritative personal history.

Every promoted model records training-data/influence lineage sufficient for correction, deletion response, rebuild or unlearning policy.

### D12 — working/activation memory

Track transient cognitive state too:

- Attention Workspace;
- current context assembly;
- active plans;
- pending tools;
- temporary summaries;
- model KV/cache generations where controllable;
- session hypotheses.

This plane matters because deletion from durable stores alone does not make a running agent forget.

### D13 — Memory Resource Manager / Scheduler

Add an explicit control plane over heterogeneous memory representations.

Responsibilities:

- activate/deactivate memory;
- move between hot/warm/cold/archive;
- schedule consolidation;
- choose reconstruction vs persistence;
- coordinate plaintext/graph/vector/episode/procedural/parametric/activation forms;
- enforce owner permissions and data classes;
- track generation/version/provenance;
- allocate memory/context budgets without imposing semantic ceilings.

This is the useful MemOS-class systems insight integrated into A.L.I.C.E.'s stronger authority model.

### D14 — Retrieval Orchestrator / Cognitive Recollection

The destination retrieval loop is:

```text
situation/query
  -> memory-need + intent interpretation
  -> retrieval plan
  -> parallel candidate generation:
       Claim / exact / source-native / episodic / graph views /
       associative activation / vector-multimodal / procedural /
       host-relationship-self / mission / live source
  -> cross-plane dedupe + authority/provenance reconciliation
  -> query-conditioned fusion/rerank
  -> evidence-consumption receipt
  -> memory-use calibration
  -> evidence sufficiency
       sufficient -> context
       insufficient -> iterative recollection / source expansion / ask / defer
```

There is no fixed "semantic fallback" hierarchy. Simple problems take fast paths. Hard problems may use the full fabric.

### D15 — Lifecycle Curator

Preserve the existing aggressive-capture/selective-retention doctrine:

- permanent compact ledger;
- bounded raw capture;
- hot/warm/cold/quarantine;
- reflection/consolidation;
- representative replay;
- storage-pressure planning;
- restore verification;
- no silent deletion of authoritative evidence.

### D16 — correction, deletion and unlearning

Deletion becomes a **cross-layer influence operation**.

The coordinator must trace:

- source object;
- event records;
- claims;
- episodes;
- graph edges/nodes;
- vector/sparse/multivector entries;
- summaries;
- workspace/context;
- active plans;
- KV/cache state where applicable;
- replay datasets;
- synthetic derivatives;
- adapters/weights/model checkpoints;
- exports/backups;
- downstream replicas.

For running-agent state, use provenance-guided checkpoint/replay semantics where exact counterfactual deletion is required.

For parametric influence, use the strongest applicable response:

- remove from future training;
- rebuild affected adapter/model;
- shard/retrain;
- verified unlearning method;
- quarantine the affected generation;
- disclose residual influence where exact removal is not technically established.

The architecture explicitly prevents memory -> parameter -> memory **recontamination** after deletion.

### D17 — Durable Workflow plane

Selected default: **Temporal** for:

- projections;
- consolidation;
- deletion;
- rebuild;
- restore;
- migration;
- model training/evaluation;
- multi-device reconciliation;
- long missions;
- self-improvement challenger workflows.

Temporal is part of the full architecture. Local self-hosting vs private cluster placement is deployment topology, not capability deletion.

### D18 — Adaptive workspace/cache

Use:

- in-process L1 for immediate tensors/objects;
- **Valkey** as the shared/distributed ephemeral workspace/cache when state crosses processes/devices.

Cache loss must never lose authority.

### D19 — model/dataset/artifact registry

Authoritative model/data lineage is content-addressed and signed/hashed.

Track:

- source datasets and exclusions;
- generators/seeds;
- training splits;
- configs;
- code revision;
- parent/child model lineage;
- optimizer/training state;
- evaluation receipts;
- deletion influence;
- promotion/rollback state.

An experiment tracker may be added, but it does not replace the authoritative lineage registry.

### D20 — multi-device and federation

First-release architecture supports continuity across devices.

Records include:

- product/host namespace;
- device identity;
- causal/logical clock;
- event position;
- encryption/custody domain;
- conflict receipts;
- reconciliation status;
- projection generations.

Private distributed deployment is allowed. Hosted-vendor dependence is not required.

## 14. Frontier-watch rule

Research continues, but the decision rule is now correct:

**Do not preserve a bad implementation because it already exists. Do not replace a good architecture just because a paper is new.**

For every finding:

- compare against the full Fable/A.L.I.C.E. destination;
- extract the capability implication;
- integrate a missing invariant/mechanism when it materially improves the destination;
- keep speculative mechanisms in research;
- do not run a technology tournament unless two implementations create a real unresolved choice;
- never optimize deployment simplicity by deleting a capability plane.
