# Memory M2 Contract-Sequence Closeout and Phase 2 Shadow-Migration Admission

**Version:** 1.0.0
**Prepared:** 2026-08-06
**Status:** M2-CLOSEOUT evaluation and preparatory admission record
**Capability ceiling:** `false`

## 1. Decision

The Memory M2.0 through M2.6 contract sequence is complete at the implemented-contract and reversible-prototype level.

This closeout does not declare the prototypes production systems. It does not transfer canonical authority, begin Phase 2 migration, activate private historical backfill, enable write mirroring, authorize canary authority, perform cutover, or unblock P5.1e.

The closeout admits the next engineering work only:

- Stage A source inventory and registration;
- Stage B read-only contract-adapter development;
- Stage C destination-candidate comparison;
- Stage E synthetic and separately owner-authorized shadow-read harness development.

The admission is preparatory and read-only. Phase 2 migration remains not started until an implementation tranche explicitly begins an admitted stage and records that state truthfully.

## 2. Evaluated M2 surfaces

The synthetic cross-prototype evaluation exercises:

1. Store Registration, Memory Unit Envelope, and Evidence Binding;
2. Claim Identity, Claim Version, Current Claim Projection, and persistent Claim Authority;
3. Evidence Relation, Claim Candidate, Conflict, Adjudication, and shadow adjudication;
4. Episode and Projection Version with graph, vector, temporal, owner, source, and self projection paths;

6. Curation Task, Curation Receipt, Durable Workflow, and Activity Event;
7. Deletion Propagation Receipt, restore filtering, rollback rehearsal, and retirement rehearsal.

The evaluator carries one synthetic lineage through claim persistence, candidate evaluation, projection, serving, workflow, and deletion rehearsal. Each persistent component must report healthy integrity before closeout succeeds.

## 4. Admitted work

### Stage A — inventory and registration

The next tranche may register Phase 2 source stores, schemas, authority roles, generations, encryption domains, data classifications, integrity state, record counts, and deletion capability.

Initial inventory remains schema- and metadata-oriented. Private row content requires the exact owner-authorized custody profile for the adapter or evaluation being executed.

### Stage B — read-only contract adapters

The next tranche may implement adapters that translate Phase 2 records into neutral evidence, claim, conflict, correction, and deletion candidates.

Adapters must record:

- source identity and digest;
- mapping version;
- unsupported fields;
- ambiguity and information loss;
- source authority;
- deletion and correction lineage;
- deterministic replay identity.

Adapters do not invent missing provenance.

### Stage C — destination candidates

Existing reversible M2 prototypes may be compared as destination candidates. Embedded SQLite remains a reference challenger rather than a destination restriction. Relational, distributed, event, graph, vector, object, workflow, and hybrid successors remain authorized.

### Stage E — shadow-read harness

Synthetic fixtures and separately owner-authorized workloads may compare Phase 2 reads with successor reads for:

- authority correctness;
- retrieval quality;
- conflict and correction behavior;
- latency and staleness;
- privacy and product isolation;
- deletion and restore filtering;
- explanation and retrieval trace quality.

## 5. Not activated by this closeout

This closeout does not activate:

- historical private-data backfill;
- controlled write mirroring;
- canary Claim Authority;
- production serving influence;
- production deletion;
- canonical authority transfer;
- cutover or Phase 2 retirement;
- P5.1e storage admission;
- Friday state transfer.

These remain governed by their own exact evidence, authority, rollback, deletion, privacy, and owner-approval gates. They are not permanently prohibited.

After this closeout merges, begin Phase 2 shadow-migration Stage A and Stage B as one reversible tranche:

- inventory and register Phase 2 sources without making discovered files authoritative;
- implement deterministic read-only adapters against synthetic fixtures;
- produce mapping, ambiguity, loss, deletion-lineage, and reconciliation receipts;
- retain Phase 2 as the compatibility baseline and test oracle;
- keep production writes, private historical backfill, canary, and cutover outside that tranche.

Starting that tranche will be the first point at which the repository may truthfully record Phase 2 shadow migration as started.
