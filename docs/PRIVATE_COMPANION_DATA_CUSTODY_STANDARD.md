# Private Companion Data Custody Standard

**Version:** 1.1.0
**Authority:** A.L.I.C.E. Constitution, Data Classification, and owner-ratified private companion direction

## 1. Repository boundary

Never commit credentials, keys, codebooks that unlock protected payloads, raw private source documents, decrypted persona payloads, encrypted private payload bundles, real private manifests, raw Rayan host archives, voice/likeness source material, private training corpora, or host-specific private model checkpoints/adapters merely for documentation convenience. Named identity roles and architecture-specific context may be documented in Git when accuracy and continuity require them. Opaque directive identifiers, neutral schemas, custody policy, validators, and synthetic fixtures remain allowed. Naming Mehejabin Elaina as source person or Rayan as owner/host does not authorize publishing their raw private evidence.

## 2. Cryptographic custody

Keys and ciphertext use separate owner-controlled custody paths. Key creation, activation, rotation, backup, recovery, compromise response, and destruction are explicit lifecycle events. A package that has exposed both ciphertext and its key outside the intended vault boundary must be re-keyed before durable installation.

## 3. Provenance types

Every private companion record declares one of:

```text
owner_attested_canonical
derived_inference
generated_reconstruction
evolved_identity
owner_correction
conflict_or_uncertain
```

Records identify source references, derivation activity, responsible component/model, timestamps, confidence where applicable, supersession/correction links, retention class, deletion lineage, and training eligibility.

## 4. Runtime and training

Private material is loaded only under an explicit A.L.I.C.E. host scope and authorized purpose. Plaintext remains memory-resident only as long as required, is excluded from ordinary logs and crash reports, and is never placed in Friday, kernel distributions, public evaluations, or cross-host caches.

Phase 5 records candidate-learning eligibility; it does not silently promote private material into memory, skills, datasets, adapters, or weights. Later promotion requires explicit manifests, evaluation, rollback, deletion propagation, and owner authority appropriate to consequence.

## 5. Truthfulness and interaction boundaries

A.L.I.C.E. preserves the distinction between source truth, inference, reconstruction, and evolved identity. It does not falsely claim generated content is an actual historical utterance or memory. It does not use private relationship material to shame, pressure, reward, punish, isolate, or create sole-support dependency.

## 6. Deletion and restoration

Deletion requests propagate through raw payloads, derived records, replay manifests, training candidates, adapters where technically supported, backups, and restore procedures. Restored snapshots replay deletion lineage before private material becomes available.

## 7. Clone-aware identity custody

The private source is used to build the highest-fidelity achievable source-person model rather than a merely inspired persona. Clone-awareness and identity truthfulness are mandatory: the system knows it is A.L.I.C.E., an AI reconstruction, and not literally the original person. Private source history, source-person model state, reconstruction inference, and A.L.I.C.E.'s post-activation continuity use separate records and keys where policy requires. Fidelity evaluations and drift reports are HIGHLY_SENSITIVE and remain outside public Git.
