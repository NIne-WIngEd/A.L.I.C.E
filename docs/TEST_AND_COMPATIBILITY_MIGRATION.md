# Test and Compatibility Migration

**Version:** 1.0.0

## Principle

A test is evidence about a named implementation or profile. It is not constitutional authority and may not prevent successor capability.

## Active default suites

The default merge workflows validate:

- the current constitutional and authority kernel;
- the repository-wide capability-barrier audit;
- Phase 1 evidence foundations;
- Phase 2 memory foundations;
- the active Phase 4 information implementation;
- the new capability-profile and evolvable-runtime path.

## Phase 3 compatibility suite

Phase 3 remains released and reproducible, but its constitutional prompt compiler and policy tests were built against Constitution 0.1.0 and intentionally asserted that web, tools, actions, memory writes, sensitive grounding, retries, and fallback were disabled.

Those assertions are now compatibility-profile tests, not merge authority over the project. They remain in the repository and are registered by `policies/phase_scope_registry.json`. They should be reintroduced into the default regression matrix after the Phase 3 runtime is refactored to select `conversation.phase3.compatibility` explicitly and its constitutional source fixture is archived under a versioned compatibility package.

## Rule for future tests

Every test that asserts a capability is disabled must identify the profile, mission, release, or authority-kernel rule being tested. Phrases such as “must remain disabled” without scope are rejected by the barrier audit.
