That last state is extremely important. Research on selective classification shows that allowing a system to abstain can

So our objective should not be:

It should be:

  Find a match only when we can prove it strongly enough. Otherwise refuse to match.

That fits this assessment particularly well because they require at least 4,000 matches, despite there being 10,000+ possible
products. [BetterBasket] Engineering Technical Assessment.pdf We can deliberately prioritize precision over coverage.

In simple terms, candidate retrieval works like this:
For every product in Store A, we do not compare it deeply against all 55,516 Store B products. Instead, we quickly search
Store B in several different ways and create a shortlist.
Example:

  A:
  Chobani Whole Milk Greek Yogurt Honey 5.3 oz


The retrieval system independently looks for things like:

    similar words: chobani greek yogurt honey
    similar spelling/text structure
    same core product: greek yogurt
    same brand
    compatible size: 5.3 oz
    important rare words: chobani , honey
    numbers/specifications
    category clues
    flavor/form clues

Each search produces its own ranked list. We combine those lists, remove duplicates, and keep roughly the best 60 candidates.
So instead of:

  1 A product
  ×
  55,516 B products


the Match Engine later sees only:

  1 A product
  ×
  \~60 plausible B products



What were all those slowdowns?
The first version was logically correct, but some implementation choices were wasting huge amounts of computer work.
1. Re-reading/parsing product information repeatedly

  size
  description

  brand
  size
  modifier


but Python was loading a whole row containing potentially large descriptions and metadata.
Now we precompute lightweight columns:

GPT-5 nano is basically a small, fast, cheap GPT-5 model meant for high-volume tasks like classification and
extraction. OpenAI specifically describes it as the fastest/cheapest GPT-5 variant and suitable for classification-style workloads.
(OpenAI Developers)
BetterBasket gives you API credentials for it. Their sample Python file is showing exactly how to call that deployment.

For our project, I would not use GPT nano like this:

  A product + B product
  → "Are these a match?"
  → trust GPT's yes/no


That's too uncontrolled.

  Product A information

I think your suspicion is probably right: the latest runs show the candidate pool is large enough, but GPT is converting only a
tiny fraction of it. I’m going to inspect the exact v12 system/user prompts and response parser, then compare them against
OpenAI’s current guidance for nano/small reasoning models and against the actual failure pattern in your 7,000-review run.
I found a major prompt/API issue already: v12 is using plain Chat Completions with no reasoning_effort , no Structured
Outputs/JSON Schema, no few-shot examples, and only product titles. For GPT-5.4 nano, that is leaving a lot of model
capability unused. OpenAI’s current docs explicitly position GPT-5.4 nano for classification/ranking, support configurable reasoning
effort, recommend structured outputs for schema reliability, and note that prompt quality should be validated on representative
evals. I’m quantifying how much this hurt your run before I rebuild it.
There’s another prompt bug that matters a lot: the current instruction says “never match different pack counts / materially
different sizes,” but it doesn’t distinguish an explicit conflict from missing information. In this dataset, Store B often omits
count/size wording that Store A includes. That wording pushes nano toward conservative N/U decisions even when there is no
contradiction.
The prompt needs an explicit rule: missing ≠ different. Reject quantity/form/variant only when both sides explicitly state
conflicting values. That is exactly aligned with how our deterministic evidence engine was supposed to treat missing data.
