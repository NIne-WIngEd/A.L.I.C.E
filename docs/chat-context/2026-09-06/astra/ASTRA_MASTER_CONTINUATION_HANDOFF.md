## Issue G — scheduler absence semantics are currently wrong/under-specified

### Current v103 stop

The owner-returned `controller-diagnostics.jsonl` contains exactly two high-level SSH failures:

- `2026-09-06T23:41:21Z` — exit 76: `Source failure evidence differs: package-manifest.json`.
- `2026-09-07T03:10:13Z` — exit 76: `Source queue query failed; absence is unknown`.

The current local diagnostics only capture the outer SSH return code/stdout. They do **not** preserve the nested remote `squeue` exit code or stderr. Therefore the current evidence cannot distinguish a Slurm query-shape error from a transient scheduler/client error.

v103 uses:

```text

```

for a historical completed/failed job. The prior read-only host trace instead used the known-good shape:

```text

```

and then filtered for the relevant job. It returned exit 0 and no a2 row. Terminal authority came from `sacct`, which showed source job 575089 `FAILED|76:0`.

Slurm `squeue` is an **active-job** query. Historical jobs can disappear from controller memory. Site documentation explicitly notes that completed job IDs eventually become invalid to active-job commands and accounting (`sacct`) must be used for historical records.

### Resolution

Provider rule:

1. For “is anything for this user/run currently active?” use a user-wide `squeue -u <user>` query whose successful empty/nonmatching result is well-defined. Filter locally by exact job ID/name.
2. For terminal historical identity use `sacct` by job ID, with explicit start time and exact `JobIDRaw,JobName,State,ExitCode` validation.
3. Never interpret **failed scheduler query + empty stdout** as absence.
4. Persist raw `{argv, exit_code, stdout, stderr, observed_at}` for every `squeue`, `sacct`, `scontrol`, and `sbatch` call before applying semantic assertions.
5. A scheduler query failure is infrastructure evidence, not permission to create a new execution identity.

# 14. Agent handoff protocol — Astra primary, Sol fallback

Effective now:

- **Astra is primary** for A.L.I.C.E. while Astra capacity is available.
- **Sol takes over** when Astra hits its usage limit.
- Sol may also take over earlier if Astra enters a repeated-hotfix loop, loses authority lineage, proposes destructive recovery, or cannot explain the actual observed state.
- When Astra capacity resets, Astra may resume from the exact continuity state written by Sol.

This supersedes the earlier default that kept the entire project primarily in Sol.

## Before Astra stops because of limits

Astra should update, in one commit if possible:

1. `START_HERE.md` — one current executable/read-only next action.
2. `STATE.json` — actual observed state, not intended state.
3. `EXPERIMENT_LEDGER.json` — any newly completed/failed experiments.
4. a dated findings note for the latest real result.
5. exact active package/launcher hashes if an executable is pending.
6. exact current run/job IDs and lifecycle status.
7. raw evidence/result location and hashes.
8. explicit “do not rerun” list.
9. any owner approvals already granted.
10. unresolved question that Sol must answer first.

Do not leave Sol with only “package vXYZ is ready.”

## When Sol takes over

Sol must:

1. read this handoff + `START_HERE` + `STATE` + latest real result.
2. check `main`, `alice-context`, `alice-mc10b-live`, `alice-mc10c-live` heads.
3. inspect current owner-provided terminal/evidence before generating a successor.
4. preserve current execution identity unless evidence requires a new one.
5. avoid rebuilding Astra's packages merely to rename them.
6. write its completed boundary back to `alice-context` before Astra resumes.

## When Astra resumes after Sol

Astra must treat Sol's newest observed evidence and context commit as the parent. Do not resume an older Astra `READY` package if Sol already changed or invalidated its prerequisite.

## Escalation triggers — stop patching and re-audit

Either agent must stop creating successor packages and perform a deeper audit when any of these occurs:

- same failure class repeats twice.
- root cause remains unclear after a diagnostic.
- execution-layer fix changes scientific semantics.
- architecture/authority contradictions appear.
- a new attempt could waste scarce GPU/CPU allocation.
- state cannot be uniquely reconciled.
- an old result would need deletion/overwrite to proceed.
- proposed fix depends on weakening provenance or inventing success receipts.
