## What multiple runs solve

The existing `train_n0_v02_full_envelope_joint_v1.py` already implements J1 → J2 → J3 with 25-step checkpoint/DEV-selection cadence. Same-stage resume checks source, training authorization, trainer implementation, accelerator-state tree hash, objective state hash, and stage predecessor receipts before continuing. This lets a sufficiently large **single-node, two-rank** provider span several sessions, with verified durable checkpoint readback before releasing compute. It does not lower the instantaneous per-rank peak in J3. Running each macro family in isolation to bypass the registered joint step would alter co-adaptation and fail the intended J3 objective.

The trainer currently uses `Accelerator` with replicated DDP, FP16, AdamW and backbone gradient checkpointing. The P43 receipt and trainer explicitly require the measured two-rank DDP topology. FSDP/ZeRO or broad activation rematerialization on T4 could preserve full model capacity in principle, but this code path is not implemented or qualified. Parameter/gradient/Adam state savings alone do not prove the 85% T4 bound because P43 reserves ~10.99 GiB for backward activations at the observed J3 maxima. A sharded route would need a new versioned full-system memory contract, source-bound P42/P39PN/P43-equivalent receipts, distributed optimizer/checkpoint/resume and DEV behavior; no silent substitution of an FSDP job for the current DDP PASS is permitted. Prefer the already specified DDP route on available high-memory hardware before creating that engineering branch.
