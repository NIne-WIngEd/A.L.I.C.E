## What FBM should capture as training material now

One compact method trace per operation family is enough for the public notebook. A trainable case needs more than a prose lesson:

1. **Input snapshot:** task, eligible evidence and source roles, interface topology, stage, data manifest, current artifacts, source/producer revisions, and permitted action. Use safe hashes or fictional payloads on the public branch.
2. **Choice set:** proposed operation, viable alternative, seductive shortcut or invalid operation, and an explicit stop/defer option. Do not automatically call every nonselected alternative wrong.
3. **Checkable target:** structural invariant, actual test that executes it, empirical observation, and whether the conclusion depends on a source, model, or unrun assumption. A static test cannot serve as a substitute for learned capability; a GPU memory projection cannot serve as gradient authority.
4. **Result and transfer:** error category, exact fix boundary, retained regressions, compute consumed, downstream DEV effect if measured, and what remains unobserved. A corrected CPU failure does not imply P43 or J1 success.
5. **Lineage and split:** case ID, source commit range, parent failure, generator family, source/template group, producer implementation hash, permission scope, and any later supersession. Split held-out cases by failure family and underlying source, not a paraphrase of the same trace.

The deterministic verifier can implement source cleanliness, hashes, permissions, sealed-set exclusion and checkpoint-chain checks. FBM must learn proposal, failure localization, case selection and repair when those require interpretation. Compare the learned builder against explicit scripts and simpler controllers. Promote it only when it solves held-out construction tasks and improves a complete assembled instance.
